Research tasks, parsing, and replaceable backends

A detailed tour of what happens between clicking “Research” and committing an evidence-backed claim—and exactly where another agent, model, crawler, or human workflow can be substituted.

01 · Mental model

Research is an orchestration pipeline

Epiq does not currently hand a backend a database or permission to mutate it. The web layer prepares a bounded task, the backend returns proposed findings, and Epiq alone validates and writes durable facts.

1RequestPydantic parses an API command.
2PrepareEpiq resolves schema, rows, state, and context.
3RunA replaceable runner returns findings.
4ValidateIdentity, status, JSON, and value type are checked.
5CommitEpiq writes evidence, claims, proposals, or NotFound.
Request → Prepare(DB, Request) → Backend(Task) → Parse(Output) → Commit(DB, Findings)
The security boundary: the backend proposes; Epiq commits. This is the most important property to retain when adding other backends.
02 · Request

The public research request

The core API model is ResearchCreate in src/epiq/web.py. It identifies a table, one versioned question, a mode, optional row IDs, and a UI scope.

{
  "entity_kind": "survey_platform",
  "question": "q_has_api_v1",
  "mode": "fill_missing",
  "instructions": "Prefer official API documentation.",
  "entity_ids": ["ent_qualtrics"],
  "scope": "cell"
}
FieldMeaningImportant behavior
entity_kindExact table identifier.The matrix projection must exist.
questionExact versioned question ID.Resolved before a background thread starts.
modefill_missing, add_evidence, or retry_not_found.Controls eligible cell states and write-back semantics.
instructionsHuman source or interpretation direction.Inserted into the backend’s question object.
entity_idsOptional exact row subset.Absent means all eligible rows.
scopeCell, row, column, or table.Operational metadata for UI/cancellation; it does not change epistemic semantics.

Row and table endpoints are convenience fan-out commands. They eventually create ordinary cell/column research requests.

03 · Preparation

Epiq enriches the task before dispatch

execute_research projects the current table, resolves the question, and selects targets according to mode. Each target contains stable identity information—not merely a display name.

{
  "entity_id": "ent_qualtrics",
  "name": "Qualtrics",
  "aliases": ["Qualtrics XM"],
  "attributes": {},
  "existing_value": true,
  "existing_valid_from": "2026-08-18",
  "existing_evidence": [
    {
      "evidence_id": "ev_123",
      "source_url": "https://www.qualtrics.com/support/api/",
      "source_title": "Qualtrics API documentation",
      "excerpt": "…"
    }
  ]
}

The question is also augmented with task_mode, human instructions, and research_context. That context contains project identity, table identity, peer rows, aliases, and row attributes. It exists to prevent errors such as researching Orleans, France in a Cape Cod table.

Mode affects the payload. Existing values and evidence are included only for add_evidence, where the backend must find an independent source and is allowed to disagree.
04 · Backend seam

The callable protocol

The replaceable contract is a Python structural protocol. A backend needs no inheritance and no knowledge of FastAPI or SQLite.

class ResearchRunner(Protocol):
    def __call__(
        self,
        entity_kind: str,
        question: dict[str, Any],
        entities: list[dict[str, Any]],
        progress: Callable[[str], None] | None = None,
    ) -> list[dict[str, Any]]: ...

OpenAIResearchRunner

Calls the Responses API with hosted web search, strict JSON Schema output, and streamed progress events.

defaultweb searchstreaming

CodexResearchRunner

Runs codex exec in an ephemeral read-only sandbox, passing a schema file and reading the last message from a temporary file.

local adapterread-only

Separate protocols exist for entity suggestions, field suggestions, and workspace planning. They are related capabilities, but they are not the same interface as cell research.

05 · Output

A backend returns findings, not claims

Each target row must produce one result. value_json is deliberately JSON encoded inside the structured envelope so one strict schema can carry every Epiq value type.

{
  "entity_id": "ent_qualtrics",
  "status": "answered",
  "value_json": "true",
  "source_type": "web",
  "source_url": "https://www.qualtrics.com/support/api/",
  "source_published_at": null,
  "observed_as_of": "2026-08-18",
  "source_title": "Qualtrics API documentation",
  "excerpt": "Qualtrics provides a public REST API…",
  "confidence": "high",
  "notes": "Official documentation for the intended platform."
}

For a failed bounded search, the contract is status: "not_found" and value_json: "null". This is not the same as a negative boolean claim.

StatusMeaningDurable result
answeredThe source supports a typed value.Evidence plus one or more claims.
not_foundThe bounded search did not find sufficient evidence.A research.not_found event/task, except in add-evidence mode.
06 · Parsing

Validation happens in layers

  1. Request parsing: Pydantic validates modes, scopes, lengths, and required fields.
  2. Schema resolution: Epiq verifies the table and exact question ID.
  3. Transport parsing: the OpenAI adapter reads server-sent events until response.completed.
  4. Envelope parsing: JSON text must conform to OUTPUT_SCHEMA.
  5. Value parsing: _parse_values decodes value_json; empty values are accepted only for not_found.
  6. Identity validation: findings for entity IDs outside the prepared target set are ignored.
  7. Type validation: Store._check_value_type validates every scalar before any claim is written.
Cardinality: a many-valued result is returned as a JSON array, validated element by element, and stored as separate scalar claims in the same cell.
07 · Write-back

Epiq owns database effects

Ordinary answered findings become an immutable source/evidence fragment and typed claim. The actor is currently recorded as agent:codex even when the default runner is OpenAI—one sign that backend identity should become explicit.

ACanonicalize sourceCreate/deduplicate source and evidence.
BValidate valueCheck Epiq type and cardinality.
CChoose timeObserved date, source date, or unknown basis.
DAssert claimAppend evidence-backed claim events.
EReprojectUI observes the new current cell.

Reference-valued findings are different: unknown related entities become provisional relationship proposals. Human approval creates and links those rows. This prevents an agent from silently expanding relational tables.

08 · Modes

One runner, three epistemic intentions

ModeEligible statePurposeSpecial rules
fill_missingUnaskedFind an initial answer.NotFound is recorded when evidence is insufficient.
retry_not_foundNotFoundRetry after human correction or guidance.Closed-world negative inference requires an authoritative exhaustive source.
add_evidenceAnsweredFind another independent observation.Existing sources are supplied and duplicate URLs rejected; conflicting values are retained.

Column research fans out into one job per eligible cell. Row research fans out across unanswered questions. Table research fans out across both. This is why results can appear incrementally and why a backend contract can remain cell-oriented.

09 · Jobs

Operational jobs are not epistemic records

A background job is mutable execution state stored in agent_jobs.payload_json: queued/running/completed status, progress messages, counters, cancellation flags, errors, and provisional suggestions. It survives server restarts, but it is not the source of truth for claims.

There are currently three “task-like” structures:
1. ResearchCreate, the command intent;
2. the agent job JSON, operational execution state;
3. research_tasks, currently used primarily for durable NotFound outcomes and feedback.

This division works, but it means there is not yet one canonical, serializable research task that can be queued, exported, routed to arbitrary workers, replayed, or evaluated independently.

10 · Substitution

How to plug in another backend today

create_app accepts a research_runner. A custom adapter receives prepared objects and returns normalized findings.

class InternalSearchBackend:
    def __init__(self, client):
        self.client = client

    def __call__(self, entity_kind, question, entities, progress=None):
        results = []
        for entity in entities:
            if progress:
                progress(f"Searching internal index for {entity['name']}")
            hit = self.client.answer(
                entity=entity,
                question=question,
                project=question["research_context"]["project"],
            )
            results.append({
                "entity_id": entity["entity_id"],
                "status": "answered" if hit else "not_found",
                "value": hit.value if hit else None,
                "source_type": "report",
                "source_url": hit.url if hit else None,
                "source_title": hit.title if hit else "",
                "source_published_at": hit.published_at if hit else None,
                "observed_as_of": hit.observed_as_of if hit else None,
                "excerpt": hit.excerpt if hit else "",
                "confidence": hit.confidence if hit else "low",
                "notes": hit.notes,
            })
        return results

app = create_app(
    database="research.sqlite",
    research_runner=InternalSearchBackend(client),
)

Tests already use this seam extensively with small Python functions. What does not yet exist is a user-facing backend registry, configuration file, per-task backend selection, capability negotiation, or backend provenance in claim actors.

11 · Design gaps

What should be formalized next

Canonical task envelope

Move preparation output into a versioned, serializable ResearchTask with stable IDs, policy, budget, context, and expected output schema.

Backend identity

Record backend name, model, version, tool policy, and run ID. Stop hard-coding agent:codex.

Capabilities

Declare whether a backend supports web search, private corpora, citations, streaming, cancellation, batch execution, and relationship proposals.

Result versus commit

Persist the raw normalized result before applying it, enabling review, replay, evaluation, and alternative commit policies.

Backend selection

Allow a project default and per-task override rather than choosing one runner when constructing the server.

Evaluation

Store latency, cost, searched sources, parser failures, and acceptance outcomes so backends can be compared empirically.

12 · Proposed formal core

A cleaner backend-neutral model

Task T = ⟨id, subject-set, question-version, mode, context, policy, budget, output-schema⟩
Run U = ⟨task-id, backend-id, started, progress*, raw-output, normalized-findings, metrics⟩
Decision D = Validate(T, U.findings, DB)
Effects E = Commit(D) ∈ {claims, evidence, proposals, not-found, rejection}

This separates four things currently interleaved in execute_research: task compilation, backend execution, result normalization, and database effects. A backend would implement only:

class ResearchBackend(Protocol):
    backend_id: str
    capabilities: BackendCapabilities

    def run(
        self,
        task: ResearchTask,
        emit: Callable[[ProgressEvent], None],
        cancelled: Callable[[], bool],
    ) -> ResearchRunResult: ...
Recommended next artifact: specify ResearchTask, ResearchFinding, ResearchRun, and BackendCapabilities as versioned Pydantic models, then adapt the existing OpenAI and Codex runners to them without changing database semantics.
